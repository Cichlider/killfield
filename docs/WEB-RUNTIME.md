# Web 运行时取舍：Killfield UI + Rust/WASM 引擎

## 结论

网页展示以 `viewer/` 为入口，保留 Killfield 的视觉与手机交互，但计算只使用
`engine/` 编译出的 Rust/WASM。没有把 Rust 引擎复制回独立 Killfield JS 仓库，也没有把
两套物理同时保留。

原因：训练 Python、原生性能测试和浏览器 viewer 现在共享同一个 Rust crate。WASM 通过
C ABI 输出扁平 `f32` 渲染缓冲区，避免逐帧 JSON 和第二套物理移植。512-ray 实测密度场
约 `0.285ms`，而历史 JS 基线约 `12.2ms`；2048-ray MPC 原生 p95 约 `2.135ms`、最大
约 `4.889ms`。WASM 即使略慢于原生，仍明显低于 60Hz 的 `16.7ms` 帧预算。

## 线程与帧率

- Rust/WASM 物理与 MPC 固定 `25Hz / 40ms`，保持训练语义不变；
- `requestAnimationFrame` 按屏幕刷新率绘制；
- viewer 在相邻引擎状态之间插值坦克、角度与子弹位置，使 60/120Hz 屏幕不再显示为
  25Hz 位置跳变；
- Canvas DPR 上限为 2，避免高 DPR 手机把简单图形放大成数百万像素重绘；
- PPO HTTP 推理继续异步，迟到动作沿用上一个动作，不冻结或补跳游戏帧。

当前 MPC 仍在浏览器主线程同步调用 WASM。基准最大规划耗时低于一帧预算，因此暂不增加
Worker、SharedArrayBuffer 和跨线程状态协议；只有实机遥测重新出现超过 16ms 的长任务时
才值得引入 Worker。

## 键盘输入链路与粘滞来源

1. 浏览器 `keydown` 把键加入当前按下集合，`keyup` 立即移除；窗口失焦会清空全部按键，
   避免丢失 `keyup` 后永久卡键。
2. 每个 `40ms` 物理 tick 只读取采样瞬间仍按住的键：按住为 `1`，未按为 `0`。没有按下
   时长队列，也不保存已经松开的移动、转向或开火命令。
3. JS 在 `kf_step` 前调用 `kf_set_input(..., continuous=1)`；Rust 物理按该 tick 的连续比例
   移动和旋转人类坦克。
4. `requestAnimationFrame` 只负责在前后物理状态间插值显示，不提高输入/物理的 25Hz
   更新频率。
5. 人类对战时，本地玩家不再显示“上一帧到当前帧”的滞后插值，而是由 WASM 克隆轻量沙盒、
   使用真实墙体/贴墙求解器计算下一姿态，再从当前权威姿态向它显示预测。预测不会先穿墙再
   回弹；AI、子弹运动与胜负仍以 Rust/WASM 的 25Hz 帧为准。
6. 人类对战每个 `requestAnimationFrame` 最多补算一个物理帧。浏览器或 MPC 偶发卡顿后会
   丢弃已经过期的整帧时间债，不连续重放多次规划；观看与自对战仍保留原有的有界追帧。

旧版会累计真实按下毫秒数，并在固定步进补帧中继续消费，导致用户松键后仍重放历史输入。
现在补帧也只使用最新按键集合：`keyup` 后所有后续 tick 都是 0，不再产生输入积压尾巴。
代价是小于一个 `40ms` 物理帧、且完整落在两次采样之间的极短点击可能不产生动作；普通人类
按键时长远高于这个范围。25Hz 物理仍意味着输入事件要到下一 tick 才改变权威物理状态。
显示预测让移动和转向在屏幕刷新帧上立即起效。人类开火是例外：按下沿会立即在权威引擎中
创建静止的新子弹并播放声音，子弹仍遵守原规则，到下一个物理帧才开始移动；按住不会连发。

## 人类 vs Killfield 开局停顿

人机模式提供 `0.0–3.0s` 的 Killfield 开局停顿 panel，步长 `0.1s`、默认 `0.5s`，设置保存
在浏览器本地并从下一回合生效。回合物理和人类键盘/摇杆立即运行；WASM 只暂停 tank 0 的
MPC，并在倒计时结束后重新启用。子弹、碰撞和人类移动不会像旧实现一样被全局冻结。

## 人工控制与 PPO Action 的边界

PPO 的 Movement 129 类是 128 个世界方向 + STOP，底层只前进。网页人类输入走完全独立的
一条链路：JS 先解析成 `forward/backup/turnLeft/turnRight` 四个 `0–1` 强度，再交给
`kf_set_input(..., continuous=1)`，和键盘共用同一个入口，不触碰 checkpoint 的 Action
contract。

左侧摇杆有两种可选方案，选择存在浏览器本地：

- **方向键（八向，默认）**：圆盘切成八个 `45°` 扇区，每个扇区等价于按住一组方向键
  （左=左转、左上=前进+左转……）；圆心是死区，半径线性映射到强度，rim 处正好等于键盘满按。
  因此它的转向上限就是键盘的 `10°/帧`，没有任何键盘到不了的速率。
- **三指按键**：三组数字按键（前后 / 左右 / 开火），按住即为 1，与键盘逐位等价；两组方向
  键各自有位置、按键大小与组内间距，开火键另有位置与大小；调整模式下可拖手柄整体移动。
  切换到该方案时八向摇杆在窗口与全屏下都隐藏（全屏左栏规则优先级更高，隐藏规则带
  `!important`）。
- **轮盘（128 方向）**：世界朝向控制，坦克自动对准摇杆方向；Page 的「前向对齐」滑杆可以在
  `0°–360°` 间调整，默认 `360° / 360°` 完全禁用后退，另有「瞬间转向」开关。

八向方案有两种形状，另有第三种方案「三指按键」（左手前后、右手左右、开火独立，位置与
大小均可调）；手感同样只是客户端映射：圆形（中心区 / 过渡区 / 四条角度分界线）与
方形（`3 × 3` 九宫格，无过渡区）。面板里的滑杆由 `viewer/src/pad.js` 的 `PAD_TUNE_FIELDS`
生成，盘面图案、手柄位置与实际按下的格子都由同一份 `padLayout()` 派生，所以画面不可能和
输入不一致；设置保存在浏览器本地并支持整份 JSON 导出/导入。每条分界线对应一个参数，拖动
一条只改变它自己；推进满速区（方形是离开中心格）时输出仍然精确等于键盘。

两种方案都在跨过 FFI 之前解析成同样的四个强度，所以物理、渲染预测和排位录像都不需要知道
玩家用的是哪一种；也不会无声修改 checkpoint 的 Action contract。

## 手机展示

- 左侧八向移动摇杆（或轮盘），右侧独立开火；
- 摇杆的格子、分界线与方向图标由 `src/pad.js` 按当前手感生成，只在该方案启用时显示；
- 按住时只高亮当前那一格：格子填色 + 该方向边缘发光（中心格没有方向，只填色）；
- 打开「手感设置」面板即进入调整模式：摇杆固定到视口上方，分界线上出现可拖动手柄；
- 触控层可隐藏和恢复；
- 支持元素全屏及固定定位回退；
- 支持时调用 Screen Orientation API 锁定横屏；失败时显示关闭竖屏锁并旋转手机的提示；
- `manifest.webmanifest` 为添加到主屏幕的 Web App 声明横屏偏好。
